Plugin interface rename and mapping

Every registered interface in GeoIPS, the name it carries today, and the name it carries under the v2.0.0 Plugin / PluginConfig split. Nothing here is committed — this worksheet exists so the naming can be argued with before it lands in the Specification.

Plugin
What is currently called a class-based plugin. Python, implements behavior.
PluginConfig
What is currently called a YAML-based plugin. Declarative, configures a Plugin.

Every PluginConfig interface maps to exactly one Plugin interface. Several PluginConfig interfaces may map to the same Plugin. A Plugin interface does not require a PluginConfig.

Kind is the singular form of the registered interface name — the value a workflow step gives to kind to select which interface resolves the step. The column below shows the new kind; the value it replaces is the singular of the current interface name on the same row. Renaming an interface renames a value that appears in every existing workflow, which is what the deprecation register at the foot of this page exists to absorb. 

steps:

Open questions this table raises

Dynamic sectors are deferred

sector_adjusters, sector_metadata_generators and sector_spec_generators are deliberately absent from the table. Consolidating them into a single DynamicSectors / DynamicSectorConfigs pair is recorded as a tabled design topic rather than decided here. They keep their current names until that discussion concludes, and whether the new Sectors Plugin relates to them is deferred along with it.

Two names change meaning rather than disappearing

sectors and workflows register PluginConfig interfaces today. Under this map each becomes the name of a Plugin interface, while the existing interface moves to sector_configs and workflow_configs. The old name stays valid and starts meaning something else.

Every other rename in the table can be handled by aliasing the old kind to the new one. These two cannot: a workflow step reading kind: workflow is ambiguous between the interface the author meant and the one the name now denotes. The deprecation register needs a deliberate answer for these two rows — which is the reason they are called out here rather than left to the register.

Products and ProductDefaults reach Workflows through conversion

Both are backwards-compatibility surfaces. A Product is converted into a WorkflowConfig at runtime and executed by the Workflows Plugin, so the one-Plugin-per-PluginConfig rule is satisfied through that conversion rather than by giving either its own Plugin.

Their names do not change. Renaming a surface that exists only so existing configurations keep working would defeat the reason it exists.

Deprecation requirement

Current kinds continue to be accepted, and raise a deprecation warning when encountered. Every rename in the table therefore produces a deprecation-register entry carrying an old kind, a new kind, a warning, and a removal schedule. No rename lands without one.
